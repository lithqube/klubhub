# KlubHub DJ — Product Connectivity Plan

This plan makes the existing product **genuinely connected**: the frontend, the
Go API, and the storage layer agree on payload shapes, every visible UI
element either does something real or is honestly labelled as a stub, and
incomplete features are not dressed up as working.

It sits beside (not inside) the v1 release-engineering plan at
`.hermes/plans/2026-09-15_004022-v1-prod-release.md`. The release plan owns
secrets, CI, container hardening, compose, and image pipeline. This plan owns
**what the running product actually does** when a user clicks something.

All findings below are grounded in the source citations produced by the five
hand audits performed in this session. Nothing here is invented. Where a fix
is plan-only and depends on a runtime exercise (e.g. "does image X survive
the worker"), the dependency is called out in the task.

> **For Hermes:** Use subagent-driven-development skill to implement this plan
> task-by-task.

## Goal

By the end of this plan, every action a user can take in the KlubHub DJ UI
either:

1. **Hits the real backend route and persists or retrieves real data** — or
2. **Is clearly labelled as a placeholder** (not decorated with green "saved"
   toasts) — or
3. **Is hidden until its backend exists**.

The dashboard and finance pages stop presenting fabricated numbers. The
tracklist, social, and EPK modules wire their existing endpoints with the
correct payload shapes. The gig module gains the relationship data its UI
already expects (venues, contacts, tracklists). The download endpoints remain
secret-gated. Social retry and image-persistence paths are verified to work,
not just compiled.

**Non-goals (explicitly):** add a finance module; build a multi-tenant auth
boundary (still P0 in the release plan); change the visual design; introduce
new product features (these are correctness repairs).

### Other assumptions (defaults; user can override)

- **Conventions.** The frontend uses both snake_case (types/gig.ts,
  types/tracklist.ts, types/social.ts where it does — *partial camelCase*
  in social) and camelCase (types/epk.ts is camelCase). The Go code uses
  *no json tags* on `Tracklist`, `Gig`, `Track` and explicit snake_case
  tags on `EPKContent` and `ScheduledPost`. **Decision (this plan):** the
  Go side becomes the source of truth; both `Tracklist`, `Gig`, `Track`
  get json tags matching what the frontend *already* uses for those types
  (camelCase where the frontend is camelCase; snake_case where the
  frontend is snake_case). EPK will be aligned to camelCase to match its
  own frontend type. Social is already partially aligned; we keep its
  snake_case JSON wire and **fix the frontend FormData names** to
  snake_case. Document the choice in `docs/CONFIGURATION.md`.
- **New API envelope convention.** `GET /api/v1/{module}/...` endpoints
  return `{ "data": ... }`. **Existing plain-array handlers** (gig list/get,
  tracklist get's nested object, social accounts, social posts) are
  migrated to `{ "data": ... }`. The store helpers tolerate both today
  (gig store does, social store doesn't) — after the migration the social
  store can be simplified.
- **Mock environment policy (confirmed by user).** Keep useful mock data in
  development and staging. Production builds must not include, import, or
  render mock fixtures or mock API handlers. Use an explicit environment gate
  rather than `v-if="false"` or a runtime fallback that could activate in
  production.
- **Finance page** remains a useful mocked preview in development/staging,
  clearly labelled `DEMO DATA — FINANCE NOT YET WIRED`; unfinished actions
  are disabled and labelled `COMING SOON`. In production, render the honest
  `PHASE 5 — NOT YET WIRED` empty state and exclude the mock fixture module
  from the production bundle. The three dashboard widgets use real API data
  in production; development/staging may use explicitly labelled mock data
  when the backend has no records.
- **Image persistence** for social posts: the simplest working model is to
  upload the bytes to a new `POST /api/v1/social/posts/{id}/image` (or
  upload-during-create) and have the worker use the resulting object key
  instead of trying to download a presigned URL the frontend never stored.
  **Decision (this plan):** add a `POST /api/v1/social/posts/{id}/image`
  route that uploads to Garage and writes the path back to
  `scheduled_posts.image_minio_path`. The composable in
  `social/store.ts` becomes two-step: create post (no image), upload
  image (gets `image_id`), then `image_id` is sent on a subsequent PATCH.
  This unifies with the existing "image_id" field and avoids multipart
  ambiguity. The store's dead `downloadImage` is removed.

## Approach (high level)

Five task groups, executed in dependency order. Each group ends with the
relevant tests green before the next starts.

```
A. Contract tests              ──► real Go HTTP tests assert on real wire
                                  shape for every endpoint the UI uses.
B. Repair payload shapes       ──► align Go JSON tags ↔ frontend TS types
                                  for tracklist, social, EPK, gig.
C. Wire routes                 ──► social image upload; gig relationships
                                  (venues/contacts/tracklists); finish
                                  PDF storage path; remove the dead
                                  downloadImage.
D. Honest UI                   ──► dashboard pulls real data with empty
                                  states; finance clearly labelled
                                  "phase 5 — not wired"; remove fake
                                  success toasts that fire on no-op
                                  saves.
E. Verify retry + persistence  ──► docker compose smoke that proves a
                                  scheduled post with an uploaded image
                                  actually surfaces through the worker
                                  (or fails with a clean error).
```

Each task group ends with `pnpm nx run-many -t test` and `go test ./...
-race` green before the next group starts. Group E adds a runtime check
that depends on Docker being available; if Docker is not available the
runtime check is marked "deferred to CI" in the task.

## Risks, Tradeoffs, and Open Questions

- **Envelope migration.** Adding `{data: ...}` to gig handlers is a
  breaking change for any external consumer. Today the only consumer is
  the in-tree frontend, which tolerates both via the existing
  `Array.isArray(...)` check. After this plan, the helper in
  `apps/dj/app/stores/gig.ts:51` can be simplified to `result.data`.
- **JSON naming for Tracklist.** Aligning to the frontend's camelCase
  means any future API consumer (mobile, CLI) will see camelCase for
  tracklists but snake_case for gigs. Document the convention in
  `docs/CONFIGURATION.md` and add a comment in `tracklist/model.go`.
- **Image persistence path.** The two-step "create post, then upload
  image" pattern means a failed upload leaves a dangling scheduled
  post. Acceptable for v1; document in the UI as "Post scheduled —
  image pending".
- **DjName in PDF.** If wiring `settings.DJName` into the PDF path
  proves more invasive than expected, fall back to a literal
  configured via env (`PDF_DJ_NAME`).
- **Finance.** This plan does not build the finance module. The
  finance page is intentionally honest about that. Phase 5 ships it.
- **Suspicion to verify before merging this plan:**
  - The image-persistence bug (worker reads `""` from
    `scheduled_posts.image_minio_path` when frontend uploaded an
    image) is currently a Suspicion. Run the docker-compose
    verification recipe from Group B's "Social — retry logic"
    section before declaring this plan's C.1 fix matches reality.
  - The `updateGig` 409 path is currently a Suspicion. Verify with
    `curl -X PUT -H "Content-Type: application/json" -d '{}'
    http://localhost:8080/api/v1/gigs/<id>` after creating a gig.
