# KlubHub DJ — First Public Production Release Plan

This plan prepares the v1 codebase for the first public production release:
hardened published images, a dedicated production Compose file, release
engineering, CI/security gates, and fixing the verified application and
deployment bugs that would otherwise break a release day.

It is an incremental consolidation on the
[`docs/v1-release-plan.md`](../../docs/v1-release-plan.md) Phase 9 blueprint,
re-grounded in the current source. Findings already verified in the three
audits (file:line citations) are first-class inputs here; nothing is invented.
Findings labelled “Suspicion” need a runnable verification step before being
treated as release blockers.

> **For Hermes:** Use subagent-driven-development skill to implement this plan
> task-by-task.

## Goal

Ship **KlubHub DJ v1.0.0** as a self-hosted, single-user open-source release
with:

- Published, immutable, multi-arch `ghcr.io/lithqube/klubhub-dj/api`
  and `…/frontend` images.
- A dedicated `docker-compose.prod.yml` that defaults to **localhost-bound**
  services and pulls only those pinned images.
- A clean backup/restore pipeline that passes a from-scratch drill.
- A green CI pipeline on every PR and on tag, with security gates that block
  high/critical CVEs in Go and JS.
- All application-level blockers named in the audits fixed.

**Non-goals (explicitly):** multi-tenant auth, billing, Kubernetes,
multi-platform social posting, hosted EPK pages, mobile app. These match the
stated v1 constraints in `docs/v1-release-plan.md`.

## Approach (high level)

The release is decomposed into **eight task groups**, executed in dependency
order. Each group ends with a CI pipeline going (re-)green before the next
group starts. Tagging `v1.0.0` is the last task, not the first.

**Architecture scope for v1.0.0:** single platform `linux/arm64` only.
This keeps CI fast (no QEMU emulation, no cross-arch test matrix), halves
image-matrix debug surface, and matches the most common single-board /
ARM-server self-hosting hardware. `linux/amd64` is **explicitly deferred**
to a follow-up release; any guest on amd64 must run a QEMU-emulated
container or wait. SELF-HOSTING.md will document this as a v1.0.0
constraint, and the README's published-image badge will call out the
arm-only manifest so users do not pull and silently fall back to emulation.

```
A. Foundational secrets/CI/lint gates        ──► CI green on lint, secret-scan,
                                               vuln-scan, typecheck.
B. Backend hardening (Go)                    ──► healthcheck, migrations, shutdown,
                                               OAuth state, calendar/PDF, request
                                               limits.
C. Storage / ops hardening                   ──► backup/restore drill, Garage
                                               bootstrap, .dockerignore, non-root,
                                               pinning.
D. Frontend / Nuxt hardening                 ──► deterministic prod proxy,
                                               mock exclusion in prod, build
                                               reproducibility.
E. Production compose + docs                 ──► docker-compose.prod.yml, README,
                                               SELF-HOSTING.md, CONFIGURATION.md,
                                               CHANGELOG, upgrade runbook.
F. Published image pipeline                  ──► GHCR arm64 builds on tag;
                                               README badges link to digest.
G. Release-day checks (tag, dry run)         ──► fresh-host `compose pull && up`.
H. v1.0.0 tag + GitHub Release               ──► one-time cutover.
```

A pre-execution assumption-check call narrows unknowns before group A starts.

### A.1 Add `.dockerignore` files

**Files:**
- Create: `/Users/admin/dev/klubhub-dj/.dockerignore` (root, used when GHCR
  build context is repo root).
- Create: `/Users/admin/dev/klubhub-dj/api/.dockerignore`.
- Create: `/Users/admin/dev/klubhub-dj/apps/dj/.dockerignore`.

**Why:** Both Dockerfiles use `COPY . .`. Without ignores, `.env`,
`garage.toml`, `backups/`, `.nx/cache`, `node_modules`, `.git`, `.claude/`,
`.opencode/` bake into build context. Mitigates accidental secret
publishing in image layers even though `.gitignore` is correct.

**Acceptance:** `docker compose build --no-cache` produces an image whose
runtime environment contains no `.env`, `garage.toml`, or `backups/` paths.

### A.2 GitHub Actions workflow: CI on PR/push and tag pipelines

**Files:** Create `.github/workflows/{ci,image,scan}.yml`.

Per the **verifying-infra-as-code** skill, every workflow must be checked with
`actionlint` and parsed with PyYAML. Pin actions by SHA.

- `ci.yml` — runs on every push/PR to `main`:
  `actionlint` on its own file, `npm run lint`, `pnpm nx run-many -t typecheck`,
  `pnpm nx run-many -t test`, `cd api && go mod download && golangci-lint run
  ./... && go test ./... -count=1 -race`. Upload coverage (`coverage.txt`,
  `api/coverage.out`) as artifacts.
- `scan.yml` — `gitleaks/gitleaks-action@pin` and
  `github/codeql-action/init@pin` on push/PR; SARIF uploads.
- `image.yml` — multi-arch build-push to GHCR on tag matching `v*.*.*` and on
  manual `workflow_dispatch`. Uses `docker/setup-buildx-action` with BuildKit
  cache, `docker/metadata-action` for tags/labels, `docker/build-push-action`
  with `provenance: true`, `sbom: true`. Built digest stored in
  `ghcr.io/lithqube/klubhub-dj/api@sha256:…` and `…/frontend@…`.

**Step-by-step (Task A.2.1-2.4):** see full plan file (each flow written
out below).

#### Task A.2.3 Workflow file: image.yml

- Capture provenance attestation via build-push `provenance: true`.
- Required secret: none beyond `GITHUB_TOKEN` (uses GHCR OIDC-aware login).
- Post-build sanity step: `docker buildx imagetools inspect
  ghcr.io/${IMAGE}:${TAG}` must show `Platform: linux/arm64` and no

## Risks, Tradeoffs, and Open Questions

- **Auth scope:** Production hardening does not yet include multi-user
  auth. Until authentication lands (out of scope for v1.0.0), the
  hardening is honest about its limits in `SECURITY.md`. This is the
  single most exposed risk. Mitigation: bind to localhost by default,
  publish an explicit reverse-proxy example that includes mTLS or VPN.
- **Phase 4 gaps:** If the user chooses to ship with the three gaps
  (tracklist linking, venues/contacts list, Copy-from-Previous),
  release notes must be honest about them. They are not security
  issues but they are user-visible product gaps.
- **Distroless vs scratch:** Moving off `scratch` enlarges the API image
  marginally (~10–15 MB). The trade is no-shell healthcheck without
  busybox.
- **`govulncheck` failure: first run may flag transitive findings
  already in `go.mod`. We triage and either upgrade or document
  acceptance as a one-line in CHANGELOG.
- **Action pinning:** all third-party actions pinned by SHA in workflows
  to avoid compromised publisher scenarios (verifying-infra-as-code
  pitfall E).
- **Calendar token rotation:** rotating the iCal token is breaking for
  clients that have a copy. Document rotation impact in
  CONFIGURATION.md and SECURITY.md.
- **GHCR anonymous pulls:** GHCR public packages can be pulled
  anonymously. We accept that. Private backups remain the user's
  responsibility.
- **Q for the user (group H.2):** do you want a release branch
  (`release/v1.0.0`) cut from `main` first, or tag directly on `main`?
  Default: tag directly on `main`.
