# KlubHub DJ v1.3.0 — Booking outreach, safe updates, amd64 images

Released 2026-11-25. The full list of changes is in
[`CHANGELOG.md`](../../CHANGELOG.md#130---2026-11-25); this page is the
operator's view: what is new, what to do when upgrading, and how the image is
published.

A project by EUN Records (Berlin).

## Headline

- **Availability and booking outreach (Phase 4.10).** DJs publish open dates,
  match them against promoter slots and send booking requests from templates
  with the EPK attached. Sends are **off by default**: they stay blocked until
  you attest that your email provider permits cold B2B outreach (see below).
- **Safe updates.** `./klubhub update` backs up the databases, Garage storage
  and secrets before it pulls new images, checks health afterwards, and
  `./klubhub rollback` goes one version back. `./klubhub update --release`
  picks the newest final `v*` tag and skips release candidates.
- **amd64 and arm64 images.** This is the first DJ tag built for both
  platforms, and the first published automatically when the tag was pushed.
- **Tracklist plain-text export**, UI motion that respects reduced motion,
  and fixes for silent data loss in social edits, press kit and gig venues.

## KlubHub Promoter: preview

The `v1.3.0` tag also publishes `ghcr.io/lithqube/klubhub-promoter-api:v1.3.0`
(amd64 and arm64). That image is a **preview**, not a Promoter release: no
versioned Promoter release exists yet, and its data model may still change
between tags. It carries the Bookings page (talent book, open slots, matches,
composer, sent log) that pairs with DJ outreach.

## Upgrading from 1.2.0

1. **Installer users:** run `./klubhub update --release`. It takes the backup
   to `.local/backups/<timestamp>/`, moves to `v1.3.0` and checks health. If a
   service stays unhealthy, run `./klubhub rollback`.
2. **Manual setups:** back up Postgres and Garage first
   ([Operations](../OPERATIONS.md#backup-and-restore)); migrations may make an
   image-only rollback unsafe. `docker-compose.prod.yml` now defaults to
   `IMAGE_TAG=v1.3.0`. Rerun `bash scripts/setup.sh prod` with your existing
   configuration.
3. Migrations **033–035** (availability, outreach templates, booking requests)
   run on start; Promoter runs **00014–00017**.
4. **On x86** set `APP_PLATFORM=linux/amd64`; the Compose default is still
   `linux/arm64`.
5. **Outreach sends** answer `422 outreach_not_permitted` until you set
   `OUTREACH_PROVIDER_PERMITS_OUTREACH=true`. Set it only if your provider's
   terms permit cold B2B outreach; it records your decision and is not a
   compliance check. `OUTREACH_MAX_PER_DAY` (default 50) caps sends per tenant.
   Read [`OUTREACH-PROVIDER.md`](../OUTREACH-PROVIDER.md) first.

See [`SELF-HOSTING.md`](../SELF-HOSTING.md) and
[`CONFIGURATION.md`](../CONFIGURATION.md).

## Publishing the image (maintainers)

Push the `v1.3.0` tag on the merge commit. `containers-ci.yml` and
`promoter-ci.yml` build each platform natively, scan each with Trivy, merge
one tag that must list exactly `amd64,arm64`, and sign it. Then verify:

```bash
docker logout ghcr.io
docker pull --platform linux/amd64 ghcr.io/lithqube/klubhub-dj-api:v1.3.0
docker pull --platform linux/arm64 ghcr.io/lithqube/klubhub-dj-api:v1.3.0
docker buildx imagetools inspect ghcr.io/lithqube/klubhub-dj-api:v1.3.0
```

`/api -version` in the running app prints `1.3.0`. Finally run
`./klubhub update --release` on a v1.2.0 install and confirm it ends on
`v1.3.0` with healthy services.
