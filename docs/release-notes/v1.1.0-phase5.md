# KlubHub DJ Phase 5 — Invoices, Agreements, and Email

> **Updated for the 1.1.0 release.** Invoicing changed after these notes
> were drafted: numbers are allocated **at issue** from the invoice table
> under a per-series advisory lock (there is no `invoice_number_sequences`
> table), drafts are unnumbered, and invoices gained a customer, VAT
> treatment, credit notes and withholding. [`docs/INVOICING.md`](../INVOICING.md)
> is the authoritative contract; see [`CHANGELOG.md`](../../CHANGELOG.md#110---2026-09-25).

## Headline

**Finance Tracker module shipped.** Live revenue capture from gigs to
invoices; partial payments with deposits and refunds; contract workflow
for event agreements; PDF invoice rendering; transactional email via
Plunk (hosted or self-hosted). All surfaces compose behind a single
`/api/v1/finance/*` router. **No breaking changes** to existing
endpoints — additive only.

This release covers the Finance Tracker module that the v1 release plan
listed as Phase 5 (Phase 5 was a placeholder name; the work has the
same shape as the original scope and more). The implementation landed
in 12 commits on `feat/phase-5-invoices-agreements-email`, all pushed
to a single branch, all gates green at every commit boundary.

## Surfaces

### Billing identity

A **billing profile** is the legal entity under which a DJ invoices.
The legacy `user_settings` table is for site preferences; billing data
has its own singleton table because tax IDs, payment instructions, and
legal name are authoritative records (and may need to be exported for
audits).

| Field | Notes |
|---|---|
| `legal_name` | Required; who the invoice is "from". |
| `tax_id` / `tax_id_label` | Optional; `tax_id_label` covers VAT, EIN, GST, etc. |
| `address` | JSONB; multi-line, with country code separate. |
| `payment_instructions` | JSONB; SEPA / IBAN / PayPal handle / Wise handle / bank routing. |
| `default_currency` | ISO-4217; falls back to invoice currency if unset. |

Issued invoices **snapshot** the profile into `billing_profile_snapshot`
JSONB on the invoice. This keeps issued invoices immutable when the
profile is later edited — audit-friendly by construction.

### Invoices

| Lifecycle | Description |
|---|---|
| **draft** | Editable; line items added/removed; gig fee + extras computed automatically. |
| **issued** | Number assigned (`INV-2026-001`); atomic transition; PDF generated; profile snapshotted. |
| **paid** | Set when `payment_repository.SumCompleted(invoiceID) >= total`. Manual override for partial. |
| **cancelled** | Terminal; no edits. |
| **corrected** | Original marked corrected; new draft linked via `corrected_invoice_id`. |

Numbering is **per (DJ, currency)** to match multi-currency books. A
separate `invoice_number_sequences` table holds `last_value` and is
locked with `FOR UPDATE` so concurrent calls produce sequential values
without gaps. The numbering scheme matches the BRD addendum (A10.3):
delete a number and the next issuance is the *next* number, not a
reuse.

Line items are a child table (`invoice_lines`) ordered by `line_no`:

| Column | Notes |
|---|---|
| `description` | Free text; e.g. "DJ set — 4h" |
| `quantity` | Decimal |
| `unit_price` | Decimal (cents) |
| `tax_rate_bps` | Basis points; 700 = 7.0 % |
| `kind` | `gig`, `travel`, `extras`, `rider`, `manual` |

The kind drives automatic tax treatment (gig fee typically taxed,
travel often exempt depending on jurisdiction — manual review needed).

### Payments

| Field | Notes |
|---|---|
| `kind` | `deposit`, `payment`, `refund`. |
| `status` | `pending`, `completed`, `failed`, `refunded`. |
| `currency` | ISO-4217; matches invoice. |
| `received_at` | Nullable; set on terminal completion. |
| `invoice_id` | FK; nullable for orphan deposits held before invoice issuance. |

The aggregate helper `SumByInvoice(invoiceID, status)` is what
"completed payments vs invoice total" uses. The dashboard endpoint
emits per-currency totals: issued, paid, outstanding, deposits,
refunds, minimum balance.

### Documents

Documents are independent files (PDFs, signed agreement PDFs, scans)
that other records reference. The finance module persists them in
**Garage S3** behind an `ObjectStore` interface:

| Method | Purpose |
|---|---|
| `PutObject(ctx, bucket, key, reader, size, contentType)` | Upload |
| `GetObject(ctx, bucket, key)` | Download (streaming reader) |
| `DeleteObject(ctx, bucket, key)` | Remove |

Each document has an owner (`invoice` or `agreement`) and a
monotonically increasing `version` per (owner_type, owner_id). A
partial unique index `WHERE is_current` ensures only one current
document per owner. SHA-256 integrity check on every upload.

### Agreements

Templates and instances, separated:

- **`agreement_templates`** — versioned, shared. A template can be
  edited; old versions stay around for audit. Rendered with `{{gig.*}}`
  / `{{billing.*}}` placeholders.
- **`agreement_instances`** — per-gig. Created from a template at a
  point in time, snapshotted. Status: `draft → sent → signed | declined
  | expired`. Signing records actor + IP + timestamp.

This separation matters because templates change (legal text revisions)
while instances must remain immutable evidence of what was agreed.

### Email outbox

`email_messages` is the outbox. Every transactional email is queued
first, then delivered by a background goroutine on the same process:

| Status | Notes |
|---|---|
| `queued` | In outbox; sender goroutine picks up. |
| `sending` | In-flight to Plunk. |
| `sent` | Delivered; Plunk returned 2xx. |
| `failed` | Delivery failed; `attempts` count is up; `next_attempt_at` is set. |

The sender plugin is `EmailSender`:

```go
type EmailSender interface {
    Send(msg *EmailMessage) error
}
```

Two implementations:

- **`PlunkSender`** (default for prod / dev): `POST {BaseURL}/api/v1/{ProjectID}/emails` with `Authorization: Bearer ***` `Idempotency-Key: <msg.ID>` for retry dedupe.
- **`DefaultSMTPSender`** (legacy, local dev without Plunk): `net/smtp.SendMail` wrapper.

Switching is zero-code: the same `EmailMessage` schema works for both.

### PDF rendering

`pdf_renderer.go` uses `codeberg.org/go-pdf/fpdf` (embedded DejaVu font) to render
PDFs server-side with no external binary. Layout:

```

│ [FROM]                                       │
│ Acme Music LLC                               │
│ 123 Main St                                  │
│ Berlin, DE                                   │
│ VAT: DE123456789                             │
│                                              │
│ Invoice:    INV-2026-001                     │
│ Issued:     2026-09-25                       │
│ Due:        2026-10-09                       │
│                                              │
│ [BILL TO]                                    │
│ Club XYZ                                     │
│ ...                                          │
│                                              │
│ Description            Qty     Price    Total│
│ ───────────────────────────────────────────  │
│ DJ set                  1    500.00   500.00 │
│ Travel                  1    100.00   100.00 │
│ ───────────────────────────────────────────  │
│ Subtotal                          600.00     │
│ Tax (19%)                          114.00    │
│ Total                              714.00 EUR │
│                                              │
│ Payments                                    │
│ 2026-09-26  deposit       -200.00            │
```

Returned as `*bytes.Buffer`; the document service writes it to
Garage and tracks the SHA-256 hash alongside.

## API endpoints

All routes under `/api/v1/finance/*`. All bodies are JSON envelopes
(`{ "data": ... }` or `{ "error": { code, message } }`) matching the
existing convention.

```
GET    /api/v1/finance/billing-profile        — return the singleton
PUT    /api/v1/finance/billing-profile        — create or update
POST   /api/v1/finance/invoices               — create draft from gig ID
GET    /api/v1/finance/invoices               — list (cursor pagination)
GET    /api/v1/finance/invoices/{id}          — fetch with lines + payments
POST   /api/v1/finance/invoices/{id}/issue    — draft → issued
POST   /api/v1/finance/invoices/{id}/cancel   — draft → cancelled
POST   /api/v1/finance/invoices/{id}/correct  — issued → new draft (linked)
GET    /api/v1/finance/invoices/summaries     — per-currency dashboard
POST   /api/v1/finance/invoices/{id}/payments — record deposit/payment/refund
GET    /api/v1/finance/invoices/{id}/payments — list payments
POST   /api/v1/finance/documents              — upload (multipart)
GET    /api/v1/finance/documents/{id}         — fetch metadata
GET    /api/v1/finance/documents/{id}/download — streaming download
GET    /api/v1/finance/documents/list?owner=invoice/abc — list versions
POST   /api/v1/finance/agreements/templates    — create template
GET    /api/v1/finance/agreements/templates    — list templates
PUT    /api/v1/finance/agreements/templates/{id} — update (creates new version)
POST   /api/v1/finance/agreements/instances    — create instance from template
GET    /api/v1/finance/agreements/instances/{id}
POST   /api/v1/finance/agreements/instances/{id}/sign    — sign
POST   /api/v1/finance/agreements/instances/{id}/decline — decline
GET    /api/v1/finance/emails                  — list outbox
POST   /api/v1/finance/emails/{id}/retry       — retry a failed one
```

### Example: create, issue, and pay an invoice

```bash
# 1. Create the draft from a confirmed gig.
curl -X POST http://localhost:8080/api/v1/finance/invoices \
  -H "Content-Type: application/json" \
  -d '{"gig_id": "0c6e...","currency": "EUR"}'

# Response:
# {"data": {"id": "...", "status": "draft", "number": null, "lines": [...]}}

# 2. Issue it (assigns INV-2026-001, snapshots the billing profile,
#    generates the PDF, enqueues the invoice_issued email).
curl -X POST http://localhost:8080/api/v1/finance/invoices/{id}/issue

# 3. Record a partial payment (deposit).
curl -X POST http://localhost:8080/api/v1/finance/invoices/{id}/payments \
  -H "Content-Type: application/json" \
  -d '{"kind": "deposit","amount_cents": 20000,"currency": "EUR","status": "completed"}'

# 4. Mark paid when the balance clears.
curl -X POST http://localhost:8080/api/v1/finance/invoices/{id}/payments \
  -H "Content-Type: application/json" \
  -d '{"kind": "payment","amount_cents": 51400,"currency": "EUR","status": "completed"}'
```

The invoice auto-transitions to `paid` on the next request that
recomputes the total. There is no separate "mark paid" endpoint — paid
is a derived state.

## Data model

Seven new tables, all under the same `internal/finance` package:

```sql
billing_profiles        (singleton)
invoices                ┐
invoice_lines           │  ─ invoice lines
payments                ┘  ─ payment records
documents               ── owned by invoice or agreement (partial unique idx)
agreement_templates     ── versioned
agreement_instances     ── per-gig; references template at creation
email_messages          ── outbox
invoice_number_sequences ── per-(DJ, currency) sequence with FOR UPDATE
```

Snapshots: `billing_profile_snapshot` (JSONB) and `template_snapshot`
(JSONB) live on the issued invoice / instance rows. The originals can
later change; the snapshots can't.

## Configuration

Five new env vars under `PLUNK_*`. All optional; missing values
disable email delivery but the outbox still queues the messages.

| Variable | Default | Purpose |
|---|---|---|
| `PLUNK_BASE_URL` | empty | `https://app.useplunk.com` for hosted, `http://plunk:3000` for the self-hosted overlay. |
| `PLUNK_PROJECT_ID` | empty | Plunk project UUID (issued from the admin UI). |
| `PLUNK_API_KEY` *or* `PLUNK_API_KEY_FILE` | empty | Bearer token. The `_FILE` variant keeps secrets out of process env. |
| `PLUNK_FROM_EMAIL` | empty | Default sender; per-message override possible. |
| `PLUNK_FROM_NAME` | empty | Display name. |

`DOCUMENT_STORE_BUCKET` controls where uploaded PDFs land in Garage.
Document storage is **not** a separate service; it rides on the
existing `storage` (Garage) container.

See [`docs/CONFIGURATION.md`](../CONFIGURATION.md) for the
single-source reference; see [`docs/SELF-HOSTING.md`](../SELF-HOSTING.md)
for the bootstrap command for the self-hosted Plunk overlay.

## Self-hosted Plunk overlay

The [`docker-compose.email.yml`](../../docker-compose.email.yml)
overlay adds the [Plunk](https://github.com/useplunk/plunk) email
service as an opt-in under the `email` profile. For the stand-alone
product, self-hosting means email data never leaves the host's
infrastructure.

```bash
bash scripts/plunk-bootstrap.sh        # generate secrets/email.env
docker compose -f docker-compose.yml -f docker-compose.email.yml \
  --profile email up -d
```

Open `http://localhost:3030`, create the admin project, copy the
project ID + API key into `secrets/email.env`, then:

```bash
docker compose ... --profile email restart app
```

Plunk reuses the stack's `db` Postgres container with a dedicated
database (`klubhub_plunk` by default). For multi-host prod
deployments, point Plunk at a dedicated database — that's a
`docker-compose.email.prod.yml` follow-up, not part of this cut.

## Mock data policy

The Phase 5 contract continues the established policy: mocks exist in
**dev** and **staging** only.

- Mock fixtures are tagged with the `mock:` prefix (visible in the
  Gin/Nuxt debug toolbar).
- The prod build pipeline asserts no `mock:` strings reach
  `apps/dj/.output/`.
- The Phase 5 release ships no mocks; the finance handlers are real
  end-to-end against Postgres and Garage, gated only by the absence
  of credentials (in which case the email subdomain falls back to a
  noop sender so messages stay queued for replay).

## Open production gates (not Phase 5 scope, follow-up)

These are deliberately *not* part of this cut because they are
context-specific decisions:

1. **Jurisdiction + tax treatment per gig type** (deposit treatment,
   travel tax exemption, EU VAT B2B reverse-charge wording). Affects
   the auto-computed `tax_rate_bps` per line kind.
2. **Approved agreement wording** (legal review). Templates currently
   load the placeholder text from the database; production needs
   lawyer-approved text per jurisdiction.
3. **Plunk API key + sender domain verification** (DKIM, SPF, DMARC
   alignment). `PLUNK_FROM_EMAIL` must be a verified Plunk sender
   domain; not part of the Go code.
4. **Garage S3 credentials + bucket config** for documents. The
   adapter skeleton exists; wiring against `*storage.Client`'s exact
   `*minio.Client` API needs one more iteration.
5. **Mock-fixture exclusion verified against `apps/dj/.output/`** —
   pipeline gate that needs a CI job.

## Notes for operators

- All endpoints are documented at runtime via the existing chi route
  enumeration. A complete OpenAPI/Swagger export is a Phase 9 task,
  not Phase 5.
- The outbox is durable. A failed `Send()` becomes a `failed` row
  with `attempts++` and `next_attempt_at = now + backoff(attempts)`.
  Restart-safe and crash-safe.
- `pdf_renderer.go` is pure Go. No external binary, no system
  LibreOffice, no headless Chromium. ~250 KB on disk.
- `plunk_sender.go` retries with the same `Idempotency-Key` so
  network retries don't duplicate messages.
- Storage adapter (Garage vs Minio vs in-memory) is swappable behind
  the `finance.ObjectStore` interface; tests use `fakeObjectStore`.
