## Store (`stores/rider.ts`)

Pinia setup-function style (matches `useEpkStore`):

```ts
export const useRiderStore = defineStore('rider', () => {
  // Templates
  const templates = ref<RiderTemplate[]>([])
  const saveStatus = ref<'idle' | 'saving' | 'saved' | 'error'>('idle')

  // Attachments (keyed by gigId for fast lookup)
  const attachmentsByGigId = ref<Record<string, RiderAttachment | null>>({})

  // ── Template actions ────────────────────────────────────────
  async function loadTemplates(): Promise<void> { … }
  async function createTemplate(input: RiderTemplateCreateInput): Promise<RiderTemplate> { … }
  async function updateTemplate(id: string, patch: RiderTemplateUpdateInput): Promise<RiderTemplate> { … }
  async function deleteTemplate(id: string): Promise<void> { … }

  // ── Attachment actions ──────────────────────────────────────
  async function loadAttachmentByGig(gigId: string): Promise<RiderAttachment | null> { … }
  async function createAttachment(input: RiderAttachmentCreateInput): Promise<RiderAttachment> { … }
  async function updateAttachment(id: string, patch: RiderAttachmentUpdateInput): Promise<RiderAttachment> { … }
  async function deleteAttachment(id: string): Promise<void> { … }
  async function exportAttachmentPdf(id: string): Promise<RiderPdfExport> { … }

  return { templates, attachmentsByGigId, saveStatus, … }
})
```

`saveStatus` is a plain ref (not computed) — matches EPK convention `[Phase 03-epk-press-kit-builder]: saveStatus is a plain ref (not computed) — allows direct mutation from both store and useEpkAutosave composable`.

`loadAttachmentByGig` returns `null` for "no attachment" (matches API 200-with-null response shape — the API returns `{data: null}` not 404 for missing attachments).

## Autosave composable (`useRiderAutosave.ts`)

Mirrors `useEpkAutosave.ts` exactly — module-level queue per (templateId | attachmentId), merged patches, 1500ms debounce, manual `flush()`. The composable is parameterized so the same composable handles both template and attachment editing:

```ts
type RiderAutosaveTarget = { kind: 'template'; id: string } | { kind: 'attachment'; id: string }

export function useRiderAutosave(delayMs = 1500) {

  const queues = new Map<string, { pending: object; timer: number | null }>()
  // … scheduleSave({ target, patch }) and flush(target) and flushAll()
}
```

Two reasons to add target parameterization vs two separate composables:
- One queue shared between template and attachment saves avoids a single composite component (`RiderTemplateEditor` and `RiderAttachmentEditor`) needing both composables imported
- The clean UX goal ("clean and fluent") means a single editor component can switch modes via a prop

`flushAll()` is called from the page's `onBeforeUnmount` to avoid losing the last edit, matching EPK's pattern.

## Page (`pages/rider.vue`)

Two-tab layout:

```
[ PAGE HEADER: RIDER · TEMPLATES & ATTACHMENTS ] [ SAVE STATUS ]

┌──────────────────┬───────────────────────────────────────┐
│ TAB: TEMPLATES   │ TAB: ATTACHMENTS                      │
├──────────────────┼───────────────────────────────────────┤
│ + NEW TEMPLATE   │ Filter: [ALL] [UPCOMING] [PAST]        │
│                  │                                       │
│ • Standard club  │ ─────────────────────────             │
│ • Festival heavy │ ATTACHED TO UPCOMING GIGS             │
│ • Boilerplate    │ ┌─────────────────────────────────┐   │
│                  │ │ 14 Mar 2026 — Berghain          │   │
│ (click → edit)   │ │ FROM [Standard club]            │   │
│                  │ │ [OPEN EDITOR] [EXPORT PDF]      │   │
│                  │ └─────────────────────────────────┘   │
└──────────────────┴───────────────────────────────────────┘
```

Tabs: `.tabs-bar` HUD style. Content panel: `.hud-card` or `.glass-panel`. Tab state in `ref<'templates' | 'attachments'>('templates')`.

`Templates` tab: list of `.glass` rows (matches EPK `TracklistHistory.vue`); click a row → opens `RiderTemplateEditor` in a side panel (split layout — left: list, right: editor with 4 stacked `RiderSectionField`s).

`Attachments` tab: fetches `useGigStore().gigs`, filters by date, and groups into upcoming/past. For each gig, fetches the attachment via `loadAttachmentByGig(gigId)`. Renders a `RiderAttachmentCard` per gig (the same component used inside `GigFormDialog`).

### `RiderSectionField.vue`

Reusable for any of the four sections. Props: `label: string`, `modelValue: string`, `chips: string[]`, `placeholder: string`. Emits: `update:modelValue`. The chip group renders one `.social-chip` button per chip; clicking a chip appends to the current text (with a comma separator if non-empty). Mirrors `EpkTechRiderSection.vue`'s chip pattern.

Section-specific chip constants live in a sibling file `apps/dj/app/components/rider/chips.ts`:

```ts
export const TECH_CHIPS = [

  'Own controller allowed', 'Booth PA check on arrival',

  '4× bottled water', '2× hot meals', 'Soft drinks', 'Towels', 'Green room access',
```

### `RiderAttachmentCard.vue`

Compact summary used in both the gig form and the attachments tab:

```
┌─────────────────────────────────────────────┐
│ 14 MAR 2026 — BERGHAIN           [STATUS]   │
│ FROM [STANDARD CLUB]                        │
│ Tech: 2× CDJ-3000, DJM-A9...                │
│ Hospitality: 4× bottled water...            │
│                                             │
│ [OPEN EDITOR] [EXPORT PDF] [DETACH]         │
└─────────────────────────────────────────────┘
```

Status pill:
- No attachment → muted, "NO RIDER ATTACHED"
- Attached from template → green, "FROM [NAME]" (last segment of template name in caps)
- Overridden → amber, "CUSTOM (FROM [NAME])" — derived from `templateId != null` and the attachment's four sections differing from its template's (content comparison; timestamps are not used because autosave rewrites all sections and an export or restored text would read as "custom")

## GigFormDialog integration

Add a `RiderAttachmentCard` at the bottom of the dialog, **only when** `gig.status === 'advanced'`. Below the existing notes/fees fields. The card:

- Shows current attachment status (none / from X / custom)
- "Attach rider" CTA if no attachment → opens `AttachRiderDialog`
- If attachment exists → shows the three buttons (open editor, export, detach)

The dialog calls `useRiderStore().loadAttachmentByGig(gigId)` on mount when status is advanced; refreshes when status transitions to advanced from the dropdown.
